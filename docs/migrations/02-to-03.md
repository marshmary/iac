# Migrating: tier 02 (small team) → tier 03 (team Terragrunt)

## When

- Copy-pasting a new `envs/<env>/` root per environment is routine and the
  copies drift (backend keys, provider config, tfvars).
- You add a second region or a fourth environment and duplication compounds.
- Cross-component dependencies (network → app) need explicit ordering.

## What changes structurally

```
BEFORE (02)                        AFTER (03)
envs/dev/main.tf …(full copy ×N)   root.hcl              ← shared backend/provider generate
modules/<name>/                    envs/<env>/
                                     ├── env.hcl         ← env-level locals
                                     └── <component>/terragrunt.hcl
                                   modules/<name>/       ← unchanged shape
```

Per-env root copies collapse into per-component units; Terragrunt generates
backend/provider config from `root.hcl` (state key = unit path); provider
and backend boilerplate disappears from every unit.

## Steps

1. Instantiate tier 03 (do not mutate the live tier-02 repo in one shot —
   migrate env by env).
2. Map each env root to components: usually `envs/<env>/<module-name>/`
   per module invocation you had.
3. State keys carry over: Terragrunt's `path_relative_to_include()` key is
   `<env>/<component>/terraform.tfstate` — either move old state objects to
   the new keys (`aws s3 mv` / storage blob copy / `gsutil mv`) or point the
   unit's generate override at the old key temporarily.
4. Convert each root's variables into unit `inputs = { … }`; shared values
   go to `env.hcl` locals.
5. Wire dependencies with `dependency "x" { config = "../x" }` blocks.
6. `task hcl-validate` + `task plan ENV=dev` per component; compare output
   with the tier-02 plan for the same env before applying.

## Effort

1–2 days for two envs and a handful of modules. The risky step is state-key
mapping — snapshot the bucket first (see tier-04 `runbooks/state-incident.md`
for the general recovery pattern).
