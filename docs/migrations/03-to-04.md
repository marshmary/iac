# Migrating: tier 03 (team Terragrunt) → tier 04 (large)

## When

- Multiple AWS accounts / Azure subscriptions / GCP projects appear
  (landing zones, separate prod org, sandbox).
- More than one cloud is in play and needs a unified layout.
- Platform/ security teams must gate changes: mandatory tags, naming rules,
  reviewed prod applies.

## What changes structurally

```
BEFORE (03)                      AFTER (04)
root.hcl (injected cloud)        common/{accounts,regions,tags}.hcl   ← registries
envs/<env>/<component>/          platforms/<cloud>/
modules/<name>/                    ├── root.hcl      ← per-cloud shared config
                                   └── envs/<env>/<component>/
                                 policy/*.rego     ← conftest gates
                                 runbooks/         ← ops procedures
                                 modules → separate registry repo (pinned refs)
```

The single live tree becomes per-cloud platform trees reading shared
registries; policy-as-code gates applies; modules leave the live repo for a
versioned registry.

## Steps

1. Stand up tier 04 (greenfield preferred): populate `common/accounts.hcl`
   and `common/regions.hcl` from your real org.
2. For each existing component: point its unit `terraform.source` at the
   module registry (or a vendored `modules-local/` during transition),
   move state to the new key scheme, apply a no-op plan to confirm.
3. Adopt `policy/` early — run `task policy-check` manually for a week,
   then make it a precondition for applies.
4. Port runbook habits into `runbooks/` as they occur; do not write them
   speculatively beyond the three shipped.
5. Split per-platform repos only when tier 04 itself hurts (/team-per-repo,
   review-load) — that is the documented end of this ladder.

## Effort

3–5 days including a cloud-per-platform bootstrap and registry extraction.
Do it incrementally: platform by platform, env by env; the registries in
`common/` are additive and can be adopted first.
