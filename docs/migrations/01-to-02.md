# Migrating: tier 01 (solo) → tier 02 (small team)

## When

- A second person touches the infra and `dev.tfvars`/`prod.tfvars` in one
  root stops being enough isolation.
- You catch yourself wrapping the same resources in `count = var.environment == "prod" ? …`.
- You want shared modules and a staging environment.

## What changes structurally

```
BEFORE (01)                      AFTER (02)
.                                .
├── main.tf                      ├── envs/{dev,staging,prod}/   ← full roots, own state
├── dev.tfvars                   │   ├── main.tf, <env>.tfvars, backend.tf, provider.tf
├── prod.tfvars                  ├── modules/<name>/            ← shared code
└── providers/<cloud>/* (root)   └── bootstrap/<cloud>.md
```

One root becomes three; shared logic moves into `modules/`; state splits from
one key to `<project>/<env>/terraform.tfstate`.

## Steps

1. Instantiate tier 02 alongside (`init-project -t 02 …`) — or restructure in
   place following its layout; both are supported.
2. Move reusable pieces of `main.tf` into a module (copy the `baseline`
   module shape, including README markers and tests).
3. Recreate state: the old single state can stay as the dev state —
   rename its key (or point `envs/dev/backend.tf` at the old key), then
   create fresh states for staging/prod. `terraform state mv` is only needed
   if you also split resources out of the old root.
4. Re-run bootstrap only if the bucket is new; the existing bucket gains new
   keys with zero migration.
5. Verify with `task check` and `task plan ENV=dev` showing a no-op or
   expected diff before any apply.

## Effort

Half a day including state juggling. Low risk: old state remains intact
until you explicitly destroy it.
